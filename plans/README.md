initial `find-animation-opportunities` pass and its implementation earlier in

## Recommended execution order

1. **001 first, alone.** It's the highest-leverage fix (the pose fade is
   currently non-functional after the first pose) and it touches the same
   function (`renderYogaStage()`) that 002 also edits. Land and verify 001
   before starting 002 so the diffs don't collide mid-edit.
2. **002 next.** Also edits `renderYogaStage()`, in the same active-pose
   branch 001 touches. Apply after 001 is confirmed working, not in parallel.
3. **003 and 004 can run together or in either order** — both touch
   `#yogaOverlay .closeRow button` and `#yogaOverlay .btnRow button`'s CSS
   rules, but 003 changes the `:active` scale value and 004 changes the
   `transition` timing function on the base rule; they don't conflict and
   can be done in the same pass.
4. **005 is fully independent** — a single additive line inside the existing
   `prefers-reduced-motion` block. Can be done any time, including in
   parallel with the others.

## Dependencies

- 002 depends on 001 being applied first (both edit the same block of
  `renderYogaStage()`'s active-pose branch; applying 002 against pre-001 code
  is still possible but the plan's step 4 explicitly references "the same
  block Plan 001 touches" for insertion-point clarity).
- 003, 004, 005 have no dependencies on each other or on 001/002.

## Not included in this batch

properties exist anywhere in `www/index.html`, so the same cubic-bezier

flagged as LOW/informational but deliberately left out of this batch since it
is app-wide, not yoga-specific, and the audit was scoped to yoga only. Revisit
as its own plan if a broader token-consolidation pass is wanted later.
